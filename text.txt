COREX Lab - Prompt Maestro del Proyecto
Visión del Proyecto

COREX Lab será una plataforma web empresarial desarrollada para centralizar todas las herramientas, automatizaciones y procesos operativos del equipo de Infraestructura.

No es una migración de COREX Desktop a una aplicación web. Es la evolución del producto hacia una plataforma moderna, escalable, mantenible y preparada para crecer durante muchos años.

La aplicación se desplegará inicialmente sobre Rocky Linux 9 / RHEL 9 y deberá poder ejecutarse como servicio mediante systemd, detrás de Nginx y preparada para producción.

Situación actual

Se dispone del código fuente completo de COREX Desktop (Electron), que ha sido auditado previamente.

La auditoría ha permitido identificar:

Integraciones existentes con Jira.
Integraciones con AWX.
Integraciones con Icinga.
Gestión de credenciales.
Automatizaciones Lifecycle.
Gestión de inventarios.
Notificaciones Microsoft Teams.
Automatizaciones varias desarrolladas durante los últimos años.

Todo el conocimiento funcional existente debe reutilizarse siempre que sea posible.

No se reutilizará la arquitectura Electron.

Únicamente se reutilizará la lógica de negocio.

Objetivo principal

Construir una plataforma web moderna denominada COREX Lab donde todas las herramientas compartan una arquitectura común.

Debe ser un producto fácilmente mantenible por cualquier engineer que se incorpore al proyecto.

La prioridad absoluta será:

mantenibilidad
modularidad
escalabilidad
seguridad
facilidad de incorporación de nuevas funcionalidades

Nunca se sacrificarán estos principios.

Objetivo final

COREX Lab deberá convertirse en la plataforma central utilizada diariamente por el equipo de Infraestructura para gestionar herramientas, automatizaciones, operaciones, incidencias y procesos internos desde una única interfaz moderna, segura y fácilmente mantenible, permitiendo incorporar nuevas Apps e integraciones sin comprometer la arquitectura del sistema.

Este documento será nuestro contrato de arquitectura. A partir de él, cada decisión técnica deberá responder a una pregunta: "¿encaja con la visión de COREX Lab?". Si la respuesta es no, se rediseña antes de implementar.

Además, te propondría crear dos documentos complementarios que nos van a ahorrar muchísimos problemas durante el desarrollo:

COREX Lab Architecture Decision Records (ADR): un registro de todas las decisiones importantes (por qué elegimos React, Keycloak, PostgreSQL, cómo funciona el Workload Engine, etc.), para que cualquier engineer entienda el razonamiento detrás de la arquitectura.
COREX Lab Developer Guide: una guía obligatoria para desarrollar nuevas Apps, con la estructura de carpetas, convenciones de nombres, buenas prácticas, requisitos de pruebas y checklist para que todas las contribuciones mantengan la misma calidad. De esa forma, aunque dentro de tres años haya varios desarrolladores trabajando en paralelo, la plataforma seguirá teniendo una arquitectura coherente y fácil de mantener.
Y una cosa importante, me gusta cómo está el front ahora, ¿vale? Eso no lo quiero tocar, quiero que se mantenga exactamente igual, porque he luchado mucho para llegar a este punto, hablando del front.

Eso cambia una decisión importante, y creo que es una muy buena noticia.

No reharemos el frontend. Lo preservaremos.

De hecho, lo añadiría como uno de los principios fundamentales del proyecto:

El frontend actual de COREX es un activo del proyecto. No debe rediseñarse, sino migrarse y adaptarse a la nueva arquitectura.

Yo haría una distinción clara:

UX (experiencia de usuario): se mantiene.
UI (aspecto visual): se mantiene.
Arquitectura interna: se reconstruye.

Es decir, cuando un usuario abra COREX Lab debería sentir que está usando la misma aplicación que conoce hoy, solo que ejecutándose en el navegador.

Lo que sí cambiaría

Por debajo, prácticamente todo.

En lugar de:

Botón
   ↓
IPC Electron
   ↓
main.js

Pasaría a ser:

Botón
   ↓
React
   ↓
REST / WebSocket
   ↓
COREX API

Pero el botón, el icono, la distribución, los colores y el flujo seguirían siendo los mismos.

De hecho, propongo una regla

Durante la Fase 1 del proyecto:

No se permitirá ningún cambio visual que no sea estrictamente necesario para adaptarlo a la web.

Eso tiene varias ventajas:

Los usuarios no tienen que volver a aprender la herramienta.
Podemos centrarnos en la arquitectura y la funcionalidad.
Si algo falla, sabemos que el problema es del backend y no de un rediseño de interfaz.
Reducimos muchísimo el riesgo del proyecto.
Solo haría pequeñas mejoras

Sin cambiar la identidad visual, aprovecharía la migración para añadir cosas que ahora son difíciles en Electron, por ejemplo:

Un menú lateral que pueda plegarse.
Notificaciones en tiempo real.
Estado de conexión (Jira, AWX, Icinga, etc.).
Un centro de notificaciones persistente.
Indicadores de carga.
Soporte completo para varias pestañas del navegador.

Pero siempre respetando el diseño actual.

Lo añadiría al documento maestro

Incluiría un apartado como este:

Compatibilidad visual

La interfaz de usuario actual de COREX se considera consolidada tras múltiples iteraciones y validaciones con los usuarios. Durante la migración a COREX Lab, el objetivo será preservar la experiencia visual y los flujos existentes. Los esfuerzos de desarrollo se centrarán en la arquitectura, escalabilidad, seguridad y mantenibilidad, evitando rediseños innecesarios. Cualquier mejora visual deberá ser incremental y nunca romper la identidad del producto.

Y te diría una cosa más, que creo que es importante para el éxito del proyecto: antes de escribir una línea de código nueva, quiero hacer una ingeniería inversa completa del COREX actual.

No para copiarlo, sino para documentarlo. Quiero extraer:

Todos los flujos de usuario.
Todas las pantallas.
Todas las integraciones (Jira, AWX, Icinga, Teams, etc.).
Todas las automatizaciones.
Todas las reglas de negocio.
Todas las dependencias entre funcionalidades.

Con esa información elaboraremos un Functional Specification de COREX Lab. Ese documento será nuestra referencia para garantizar que, cuando demos el salto a la plataforma web, no perdamos ninguna funcionalidad que hoy aporta valor. Creo que es la forma más segura de evolucionar el producto sin romper lo que tanto trabajo te ha costado construir.
